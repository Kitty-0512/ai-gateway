# 口头复盘（不看文档讲三个故事）

面试时尽量 **不翻笔记**。Q1–Q5 自问自答见文末。

---

## 故事 1：为什么做

业务同事问「最近 SEO 怎么样 / 为什么下降」，过去要找数、对口径、写 SQL。  
这个项目做成 **面向业务人员的 Data Agent 智能问数与经营分析**：自然语言进，SQL / 表 / 图 / 结论出，并露出 Router→Planner→Tool 过程，方便解释 Agent 没有黑盒乱答。

一句话：不是把 Text-to-SQL 做大，而是把「问数 + 经营分析」做成能验收的产品。

---

## 故事 2：怎么防止 AI 乱答

几层约束，由外到内：

1. **语义层**：流量默认 PV，SEO流量→organic_traffic，写进 Prompt，减少口径漂移。  
2. **Schema 裁剪 + 只读 SQL**：只给相关列；破坏性语句不该执行。  
3. **Validator**：生成后、执行前对字段做存在性检查（**现在误伤函数名，见失败案例，诚实讲**）。  
4. **Planner ≤3 步、一次规划**：原因分析可以先趋势再下钻，但不搞 ReAct 死循环。  
5. **结论必须看见**：有表有图也把 Synthesizer/分析文本放在上面，避免「有数没结论」。

---

## 故事 3：怎么迭代（把日期锚点当核心片段）

真实过程，不要讲成完美 roadmap：

1. 主 Demo「最近 30 天 SEO 为什么下降」一度 **SQL 成功、0 行**。  
2. 定位不是模型不会写 organic_traffic，而是 **mock 日期钉在 2024-06，SQL 用 CURDATE()**，时间坐标系不一致。  
3. 产品决策：**先只改数据生成窗口到最近 60 天**，不改 Text-to-SQL 架构，立刻复测五题——Q1/Q2/Q4 有数有结论。  
4. 把「相对数据最大日期 vs 绝对 CURDATE」写进决策表，标 **待验证**——如果再给两周，会在 Prompt/中间层注入 `max(date)` 做相对区间，覆盖用户上传的历史 CSV。  
5. 同期：Planner 在 `mode=sql` 下不再跳过规划；AnalysisView 不再藏结论。Validator/跨表校验 **明知有坑先记 Failure Case，本轮不修**，避免抹掉评测证据。

这就是「发现 → 根因 → 最小改动 → 重验 → 记下没做的架构项」。

## 自问自答 Q1–Q5（当前真实结果）

**Q1 最近7天PV是多少？**  
成功。1 步，`SUM(pv)`，结论里总量大约 18.2 万。

**Q2 最近30天SEO流量趋势怎么样？**  
成功。1 步，日级 `organic_traffic`，约 31 行，分析写持续下行。

**Q3 本周和上周自然流量相比有什么变化？**  
失败。Validator 把 `DATE_SUB`、`WEEKDAY`、`INTERVAL`、`DATE_ADD`、`NULLIF` 当成不存在的字段。对比题系统性风险。本轮故意不修。

**Q4 最近30天SEO流量为什么下降？**  
部分成功，作为主 Demo。Planner 2 步 + Synthesizer；趋势 93 行有结论；关键词下钻失败。用户能看到核心结论和表图。

**Q5 哪些关键词导致了下降？**  
失败（归因步）。关键词列不在校验用的流量表字段里，外加别名/函数误伤。生成器里其实有 Site A 掉排名的词，是系统没查到，不是没数据。

## 30 秒收尾

简单问数已经能跑通；复杂归因和日期函数对比是已知缺口；迭代方式是用评测和 Failure Case 驱动，而不是先把校验器改到没有失败。
